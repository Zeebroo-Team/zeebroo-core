Getting Started

Read this before jumping into a resource — it applies to nearly every endpoint in this reference.

Base URL

Most of the API lives under /api/v1/pos. A few modules (Developers, most of Platform Modules) have their own base paths — the full path is always shown on each endpoint card.

Authentication

1
Get a token

POST /auth/token with email + password → returns an access_token.

2
Send it on every protected request

Header: Authorization: Bearer {access_token}

Business & branch scope

Most endpoints are scoped to a business. Send one of:

  • Header X-Business-Id: {id} (recommended)
  • Query param ?business_id={id}

If omitted, the API falls back to the authenticated user's most-recently-selected business. When branch-level POS separation is enabled, additionally send header X-Branch-Id: {id}.

Response envelope

Successful responses follow { "data": … }. Lists add pagination: { "data": […], "meta": { pagination } }. Errors return { "message": "…", "errors": { "field": ["…"] } } with an appropriate HTTP status code.

ℹ️
SourceA large part of the Pos module (auth, catalog, checkout, products, sales, invoicing, purchasing, HR/payroll) has a hand-maintained OpenAPI 3.0 spec at Modules/Pos/docs/openapi.yaml, served live at /api/v1/pos/docs/openapi.yaml. This reference was built by combining that spec with a direct read of every controller for endpoints the spec doesn't yet cover.

Authentication, business/branch selection, the POS-optimized catalog, checkout, and core product/category/unit/brand/discount CRUD. Start here — everything else builds on these endpoints.

Authentication

Token issuance, user registration, business-category lookups, profile, and token revocation. The public routes (token, register, business-categories) require no bearer token; the rest require one.

POST /api/v1/pos/auth/token Create access token

Verifies email + password against users and issues a Sanctum personal access token. Send the returned access_token as Authorization: Bearer {token} on all protected routes.

Public — no auth required

Request body

ParamTypeDescription
emailstringAccount email.
passwordstringAccount password.
device_nameoptstringLabel for the issued token. Defaults to pos-api-client.

{

Checkout

Creates a completed (or scheduled) sale from a cart of items, deducting stock and recording payment in one transaction.

HR Management (core)

A webhook ingestion endpoint for physical biometric/attendance devices to push punch (clock-in/clock-out) events into the HR attendance system. Confirmed from AttendanceIngestionService: incoming punches are deduplicated, matched to an employee via an active EmployeeBiometricMapping for the device, and folded into daily AttendanceRecords.

POST /api/v1/hr/attendance/device-punches Ingest attendance device punches

Not a Sanctum route — it sits only behind throttle:api and is authenticated by a per-business shared secret sent as X-Attendance-Key, checked against the business's hr.attendance.device_ingestion_key setting (constant-time compare). Each punch is deduplicated by a hash of business+device+employee_code+punch_time+punch_type (or by external_event_id if supplied), then matched to an employee via an active biometric device mapping and merged into that day's attendance record (earliest punch as check-in, latest as check-out unless explicit in/out types are given).

X-Attendance-Key header required (per-business secret) — no Sanctum token, no session
